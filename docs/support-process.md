# Support process

The public issue is the place to follow a report. Internal implementation notes may be maintained separately; useful questions and outcomes belong on the public report.

## How reports are handled

1. **Review:** identify whether the report concerns website behavior, Minecraft information, or a feature request; check for duplicates.
2. **Clarify:** ask for the smallest missing detail needed to reproduce or assess it. Reports can remain open while information is gathered.
3. **Investigate:** reproduce the website behavior or check the relevant edition/version and evidence. Distinguish source review from in-game testing.
4. **Resolve:** explain the outcome. For a deployed fix, include the website build number and what changed. If work is implemented but not deployed, say so and keep the release outcome clear.

For duplicates, link the report being followed. For a behavior explanation or a request that will not be implemented, give a reason. Closing an issue alone does not mean a website update has shipped.

## Contributing useful follow-ups

Add new reproduction steps, affected versions, evidence, or a confirmation that a released build fixes the problem. Keep separate problems in separate reports. Subscribe to an issue for updates rather than opening another report for the same problem.

Response times depend on available project time; this tracker does not promise a response deadline or a feature delivery date.

## Scope

Documentation improvements to this support repository are welcome as pull requests. Website code changes are handled separately. Keep public reports and attachments free of private information; use [Contact Astro Atomica](https://www.astroatomica.com/contact) when a report requires private details.
